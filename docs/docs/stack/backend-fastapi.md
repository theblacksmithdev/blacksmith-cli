# FastAPI Backend

The third backend, selected with `blacksmith init --backend fastapi`. It is Python,
like Django, but small and function-first: an `app/` package you own, Pydantic for
validation and the schema, SQLAlchemy for the database, and Alembic for migrations. It
speaks exactly the same HTTP contract as the Django and Express backends, so the React
frontend is identical whichever you pick. See
[Choosing a Backend](../guides/choosing-a-backend.md) for how the three compare.

## Stack

| Layer | Technology |
|-------|-----------|
| Runtime | Python 3, run from the project's `venv/` |
| Framework | FastAPI, served by Uvicorn |
| Validation and schema | Pydantic v2 |
| ORM | SQLAlchemy 2.0 (SQLite in development, Postgres in production) |
| Migrations | Alembic |
| Auth | JWT (PyJWT) with bcrypt password hashing |
| Docs UI | Swagger UI at `/api/docs/`, ReDoc at `/api/redoc/` |
| Tests | pytest + FastAPI's `TestClient` |

## Project Structure

```
backend/
├── app/
│   ├── main.py              # the FastAPI app; routers mounted at the blacksmith: markers
│   ├── config.py            # settings from the environment and .env
│   ├── db.py                # engine, session, Base, User, utcnow()
│   ├── errors.py            # DRF-shaped validation errors
│   ├── pagination.py        # DRF-shaped page envelope helpers
│   ├── fields.py            # shared Pydantic field types
│   ├── routers/auth.py      # auth endpoints and get_current_user
│   └── posts/               # one package per resource (make:resource)
├── migrations/
│   ├── env.py               # imports app.main so every model is registered
│   └── versions/            # generated, committed
├── tests/                   # test_auth.py, test_migrations.py, one file per resource
├── conftest.py              # test database and client fixtures
├── alembic.ini
├── scripts.py               # export-openapi
├── requirements.txt
└── .env
```

## Package Anatomy

Every resource is a package with the same four modules, generated by
[`blacksmith make:resource`](../commands/make-resource.md):

| File | Responsibility |
|------|----------------|
| `models.py` | SQLAlchemy model |
| `schemas.py` | Pydantic request and response models: validation **and** the OpenAPI contract |
| `service.py` | Business logic; the only layer that queries the database |
| `router.py` | Endpoints: resolve dependencies, call the service, return the schema |

Services are plain functions that take the session and the user, so they are
callable from scripts and tests without a request.

## The API Contract

The FastAPI backend reproduces Django REST Framework's wire format, which is what
lets one React codebase work against any of the three backends.

**Pagination**: list endpoints return DRF's envelope:

```json
{ "count": 45, "next": "http://localhost:8000/api/posts/?page=2", "previous": null, "results": [] }
```

**Errors**: `app/errors.py` turns FastAPI's 422 validation errors into DRF's 400,
and leaves FastAPI's 422 responses out of the OpenAPI document:

```json
{ "detail": "Not found." }
{ "title": ["This field may not be blank."] }
```

**Field names** are snake_case (`created_at`, `created_by`). **Timestamps** are
serialized in UTC with a `Z`. **URLs** keep their trailing slash: `/api/posts/`,
`/api/posts/{id}/`.

**Operation IDs** follow drf-spectacular's convention (`posts_list`,
`posts_retrieve`, `posts_partial_update`), set with `operation_id=` on each route.
That is what gives the generated React hooks the same names on every backend.

## OpenAPI Without a Server

`scripts.py export-openapi` imports the app and writes `app.openapi()` to a file.
It never starts the server, so [`blacksmith sync`](../commands/sync.md) and CI both
work from a clean checkout. At runtime the same document is served at
`/api/schema/`.

## Migrations

Tables are created and changed only by Alembic, never at startup. After changing a
model:

```bash
blacksmith backend alembic revision --autogenerate -m "add post status"
blacksmith backend alembic upgrade head
```

Read the generated file in `migrations/versions/` before applying it, and commit it.
Migrations run in batch mode, so the same file works on SQLite and Postgres.
`tests/test_migrations.py` fails when a model has changes that no migration covers.

## Authentication

JWT access and refresh tokens with the same endpoints and response shapes as the
Django backend:

| Endpoint | Purpose |
|----------|---------|
| `POST /api/auth/register/` | Create an account, returns a token pair |
| `POST /api/auth/login/` | Exchange credentials for a token pair |
| `POST /api/auth/refresh/` | Exchange a refresh token for a new pair |
| `GET /api/auth/me/` | Current user profile |
| `PATCH /api/auth/me/` | Update the profile |
| `POST /api/auth/change-password/` | Change password |
| `POST /api/auth/forgot-password/` | Request a reset email (stub) |
| `POST /api/auth/reset-password/` | Complete a reset (stub) |
| `POST /api/auth/logout/` | Log out |

Tokens are stateless: a logged-out refresh token stays valid until it expires.
`forgot-password` and `reset-password` return success without sending mail; wire
them to your mail provider.

Protect an endpoint by depending on `get_current_user` from `app.routers.auth`.

## Environment

`.env` is generated from `.env.example`:

```bash
SECRET_KEY=change-me-in-production
DATABASE_URL=sqlite:///./db.sqlite3
CORS_ORIGINS=["http://localhost:5173"]
```

Settings are read by `pydantic-settings` in `app/config.py`. **Set a real
`SECRET_KEY` before deploying.**

## Moving to Postgres

Point `DATABASE_URL` at your database (for example
`postgresql+psycopg://user:pass@host/db`), add the driver (`psycopg[binary]`) to
`requirements.txt`, and run `blacksmith backend alembic upgrade head`.

## Tests

```bash
blacksmith test --backend
```

pytest drives the real app through `TestClient` against a throwaway SQLite database
built by running the migrations. `conftest.py` provides `api_client`, `auth_client`
and `other_client`; each signed-in client is a new user. The database lasts the whole
session, so tests create the rows they need and never assume a table is empty.

## Building for Production

There is nothing to compile: [`blacksmith build`](../commands/build.md) skips the
backend and builds the frontend only. Deploy the backend directory with its
`requirements.txt` and serve it with Uvicorn (see the
[Deployment guide](../guides/deployment.md)).
