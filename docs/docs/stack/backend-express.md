# Express Backend

An alternative to the Django backend, selected with `blacksmith init --backend express`.
It is TypeScript end to end, and it speaks exactly the same HTTP contract as the
Django backend — the React frontend is byte-for-byte identical either way.

## Stack

| Layer | Technology |
|-------|-----------|
| Runtime | Node.js 20+, ES modules |
| Framework | Express 5 |
| Language | TypeScript (strict) |
| ORM | Prisma (SQLite in development, Postgres in production) |
| Validation | Zod |
| OpenAPI | `@asteasolutions/zod-to-openapi` |
| Auth | JWT (`jsonwebtoken`) with bcrypt password hashing |
| Docs UI | Swagger UI at `/api/docs/` |
| Tests | Vitest + Supertest |

```
│   │   ├── zod.ts           # Zod extended with .openapi()
│   │   └── openapi.ts       # registry + document builder

│   ├── utils/               # errors, pagination, password, tokens

│   │   └── auth/            # schemas, service, controller, routes, tests

├── tsconfig.json

```

## Module Anatomy

Every resource is a module with the same four files, generated by
[`blacksmith make:resource`](../commands/make-resource.md):

| File | Responsibility |
|------|----------------|
| `<name>.schemas.ts` | Zod schemas — request validation **and** the OpenAPI contract |
| `<name>.service.ts` | Business logic; the only layer that touches Prisma |
| `<name>.controller.ts` | Reads the request, calls the service, sets the status |
| `<name>.routes.ts` | Express routes plus `registry.registerPath` for OpenAPI |

Services take plain arguments and return plain data, so they are callable from
scripts and jobs without a request.

## The API Contract

The Express backend deliberately reproduces Django REST Framework's wire
format. That is what lets one React codebase work against either backend.

**Pagination** — list endpoints return DRF's envelope:

```json
{ "count": 45, "next": "http://localhost:8000/api/posts/?page=2", "previous": null, "results": [] }
```

**Errors** — three shapes, all understood by the frontend's `parseApiError`:

```json
{ "detail": "Not found." }
{ "non_field_errors": ["Invalid email or password."] }
{ "title": ["This field may not be blank."] }
```

**Field names** are snake_case (`created_at`, `created_by_id`), because they are
serialized straight to JSON and the frontend's TypeScript types are generated
from it.

**URLs** keep their trailing slash: `/api/posts/`, `/api/posts/{id}/`.

**Operation IDs** follow drf-spectacular's convention — `posts_list`,
`posts_retrieve`, `posts_partial_update` — which is what makes the generated
React hooks come out with the same names on both backends.

## OpenAPI Without a Server

`npm run openapi` builds the document by importing the route modules and
reading the registry. It never starts the server or opens the database, so
[`blacksmith sync`](../commands/sync.md) and CI both work from a clean checkout:

```bash
blacksmith backend run openapi   # writes backend/openapi.json
blacksmith sync                  # regenerates frontend/src/api/generated/
```

At runtime the same document is served at `/api/schema/`, with Swagger UI at
`/api/docs/`.

## Authentication

JWT access and refresh tokens, mirroring SimpleJWT's behaviour on the Django
side — including token rotation on refresh and SimpleJWT's error wording, which
the frontend's 401 interceptor keys off.

| Endpoint | Purpose |
|----------|---------|
| `POST /api/auth/register/` | Create an account, returns a token pair |
| `POST /api/auth/login/` | Exchange credentials for a token pair |
| `POST /api/auth/refresh/` | Exchange a refresh token for a new pair |
| `GET /api/auth/me/` | Current user profile |
| `PATCH /api/auth/me/` | Update the profile |
| `POST /api/auth/change-password/` | Change password |
| `POST /api/auth/forgot-password/` | Request a reset email (stub) |
| `POST /api/auth/reset-password/` | Complete a reset (stub) |
| `POST /api/auth/logout/` | Log out |

`forgot-password` and `reset-password` return success without sending mail —
they are marked `TODO` in the controller for you to wire up to your mail
provider, exactly as the Django template leaves them.

## Environment

`.env` is generated from `.env.example`:

```bash
NODE_ENV=development
PORT=8000
DATABASE_URL="file:./dev.db"
JWT_SECRET=change-me-in-production
ACCESS_TOKEN_LIFETIME_MINUTES=30
REFRESH_TOKEN_LIFETIME_DAYS=7
CORS_ALLOWED_ORIGINS=http://localhost:5173,http://localhost:3000
```

Values are parsed through Zod at startup, so a malformed variable fails
immediately rather than deep inside a request. **Set a real `JWT_SECRET` before
deploying.**

## Moving to Postgres

Change the datasource in `prisma/schema.prisma` and point `DATABASE_URL` at
your database:

```prisma
datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}
```

Then `blacksmith backend exec prisma migrate deploy`. Note that SQLite's
`contains` filter is case-insensitive for ASCII while Postgres's is not, so
search endpoints need `mode: 'insensitive'` after the switch.

## Tests

```bash
blacksmith test --backend
```

Vitest drives the real app through Supertest against a SQLite database rebuilt
from `schema.prisma` on each run. Spec files run sequentially — they share one
database, and the setup file empties every table between tests.
